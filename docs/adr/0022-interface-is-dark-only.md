# 介面固定深色系，不隨作業系統切換

三個頁面的配色以深色系為唯一基準。不提供淺色版，也不隨作業系統的外觀設定切換——不論何時打開，畫面都是設計時決定的那一套深色。

## Context

`color-scheme: light dark`（一行 CSS 宣告，告訴瀏覽器這頁支援亮暗兩種）在三頁都有，但所有顏色值都是寫死的淺色系（`docs/interface.md` §4 的視覺語彙表）。作業系統切深色時，瀏覽器給的是深色的原生元件（捲軸、`<select>`、日期選擇器）與深色底，但頁面內容仍是淺色——最明顯的是 `#f3f4f6` 的圖片佔位底色會變成一塊刺眼亮白。

`docs/interface.md` §7.3 把這稱為「兩者之間最糟的狀態」：宣告了支援，實際上沒支援。當時列出兩條出路——補齊雙向的深色版，或拿掉宣告只做淺色。

實際的偏好是第三條：**這是個人工具，只有一個使用者，這個使用者要深色**。雙向切換是在服務「不知道偏好的多個使用者」，而這裡的偏好是已知且固定的。

## Considered Options

**補齊雙向深色版**（否決）：用 `prefers-color-scheme`（作業系統外觀偏好的媒體查詢）加一組深色 CSS 變數，亮暗都維護。否決理由是它要求維護兩套配色值，每次調色都要對兩邊；換來的彈性——跟隨作業系統——沒有人會用到，因為使用者的偏好是固定的深色。

**加手動切換鈕**（否決）：需要 JS 與 `localStorage`（瀏覽器本機記憶）記住選擇。違反 `docs/interface.md` §1 記載的性質「除了三件事以外，畫面在沒有 JS 的情況下就是完整的」，換來的還是一個不會被切走的選項。

**固定深色，單一配色**（採用）：一套顏色值，就是深色。`color-scheme` 從 `light dark` 改為 `dark`（固定值），讓瀏覽器原生元件也用深色，但不帶「會切換」的意思。移除任何 `prefers-color-scheme` 的預期。

## Consequences

- **§4 的視覺語彙表整份改寫為深色基準值。** 上漲綠、下跌紅、警示琥珀、次要灰、框線、圖片佔位底、連結藍，每一個都要在深色底上重新校對對比度（contrast，前景與背景的明暗差）。紅綠特別要注意——深色底上的飽和紅綠容易刺眼，且對色弱使用者不友善。

- **圖片佔位底色 `#f3f4f6` 必須換掉。** 它是這個問題最早現形的地方。換成深色的中性底，並與 §7.1 的卡圖框比例待辦一起處理——那塊底色到底還要不要留，本來就是 §7.1 逼出的三個決定之一。

- **`color-scheme` 宣告改為 `dark`，不是刪除。** 保留它是為了讓瀏覽器的捲軸、`<select>`、日期選擇器跟著深色；刪掉會讓這些原生元件停在亮色，又製造一次不一致。

- **這個決定不牽動任何「不可協商的約束」（§5）。** 那 11 條講的是「畫面不能說謊」，與配色明暗無關。顏色只用在數字上、漲跌用綠紅、涵蓋率量尺用中性灰——這些規則在深色底上照舊適用，只是綠紅灰的實際色值換成深色版。

- **不需要新的測試。** 沒有任何測試斷言鎖住顏色值（§6 三層清單裡沒有一條是顏色）。

- **CSS 變數（設計 token）的組織方式不由這張 ADR 決定。** 是否把 §4 的顏色抽成共用變數、放在哪裡、要不要因此推翻 §3「三頁樣式不共用」，留給 UIUX 階段連同版面重做一起決定。這張 ADR 只定「配色是單一的深色系」。

- **之後若想加淺色版，這張 ADR 可以重開。** 但預設方向已定：先做好唯一的深色系，不要為了「支援切換」先切成兩半。
