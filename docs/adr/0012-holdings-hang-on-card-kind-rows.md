# 持有品掛在卡種列上，而非已確認的卡種主檔

持有品的外鍵指向 `card_mapping_candidate`（卡種列），不指向 `card`（已確認的卡種主檔）。因此匯入不需要等卡種對應完成，推翻確認也不會讓持有品變成無主資料。

## Considered Options

**掛在已確認的卡種主檔（apparel id）上**看起來更直接——市值本來就掛在主檔上。但它有兩個問題：

第一，**開機順序死結**。匯入若要求「每一列都對得到已確認的卡種」，全新的資料庫一列都還沒確認，匯入必然失敗，服務永遠起不來。要繞開就得加一個「等對應完成才匯入」的隱形條件，那是一個看不見的狀態機。

第二，**推翻確認會產生無主持有品**。`undo_confirm` 會刪掉主檔那一列。若持有品掛在上面，推翻一個卡種就會讓你手上的實體卡在系統中消失，或逼我們加一條「有持有品就不准推翻」的限制。但那條限制在領域上是錯的：你對某張卡的 SNKRDUNK 對應判斷有誤而想重對，跟你是否擁有那張實體卡，是兩件無關的事。

卡種列由 seed 從同一份 CSV 建立，每一筆持有品必定對得到，兩個問題都不存在。要取得市值時多一次 join 即可（`card.mapping_candidate_id` 是唯一鍵）。

## Consequences

- 尚未確認、或已否決的卡種也能掛持有品。持有品清單裡 `apparel_id` 為空即代表該卡種還沒對應到 SNKRDUNK，頁面上就沒有卡圖。
- 推翻確認不再需要任何防護，維持原行為。
- 「持有品對不到卡種列」成為內部一致性錯誤而非使用者資料錯誤。程式仍明確拋錯不吞，但走不到的路徑沒有測試覆蓋。
