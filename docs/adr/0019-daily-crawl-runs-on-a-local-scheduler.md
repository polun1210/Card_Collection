# 每日爬取由本機排程觸發，不用 GitHub Actions

成交紀錄改為**每日爬取**，觸發來源是**本機的 Windows 工作排程器叫起一支 CLI 腳本**
（`scripts/crawl.py`），與 web 服務的生命週期無關。否決 GitHub Actions。

## Context

ADR-0007 記錄了 SNKRDUNK 的 `trades` 固定最多 20 筆且無分頁，並在 Consequences 開出
藥方：改為每日爬取、累積寫入本地成交紀錄表。那份藥方當時沒有數據佐證，也沒有被執行。

第一次真實全量爬取補上了數據。68 個卡種裡：

| | |
|---|---|
| 每張卡「最新 20 筆」涵蓋天數的中位數 | 6 天 |
| 20 筆只涵蓋 3 天以內的卡 | **13 / 68 張** |
| 20 筆全部落在同一天的卡 | **2 張**（Mew `S12a #183`、Mimikyu `M2a #205`） |

那 2 張一天就成交超過 20 筆。**只要有一天沒爬，那一天的成交就永久消失**——沒有分頁
可以回頭補。這不是效能問題，是資料會不會缺角的問題。

一輪爬取的實測成本：79 個請求 × 319 ms 純網路時間 ≈ **105 秒**，其中 79 秒（75%）是
禮貌間隔。成本幾乎全是「等」，不是「算」。

### 與 #8 規格的衝突判讀

#8 的規格寫著「爬取由手動觸發，**不接排程**、不掛在啟動流程上」。

該句的理由是「行情不適合當**開機條件**」——反對的是「SNKRDUNK 掛掉害服務起不來」，
不是反對排程本身。本 ADR 因此**維持「爬取永不阻擋啟動」**（`app.py` 的 lifespan 不碰
行情），只新增一個與服務生命週期無關的觸發來源。兩者不衝突。

## Considered Options

**GitHub Actions**（否決）：

1. **碰不到本機資料庫。** 它跑在用完即丟的虛擬機上，要留下資料只能 commit 回 repo
   或改用雲端資料庫。
2. **SQLite 是二進位檔，無法 merge。** 雲端與本機都寫入，遲早撞上無解的衝突；而
   ADR-0013 已寫明之後的真實來源是 CRUD，本機會寫入是既定方向。
3. **資料中心 IP 的信譽較差。** 臺銀掛著 Akamai Bot Manager，實測從家用 IP 用純
   httpx 都被擋（ADR-0017），從 GitHub 的 IP 段打過去被擋的機率明顯更高，且是做完
   才會發現的失敗。
4. **Actions 不是伺服器**，沒有網址可以給手機開。

Actions 唯一真正的優勢是失敗會主動寄信。這個優勢由死人開關（dead man's switch）單獨
取得，不必連帶承受上述四項代價。

**掛在 web 服務裡的背景排程器**（否決）：服務沒開就不會跑，而服務開著與否取決於有沒有
人記得開。這等於把「資料完不完整」綁在一個人的習慣上，且服務重啟就漏一輪。它同時違反
「爬取與服務生命週期無關」這條界線。

**本機工作排程器 ＋ CLI 腳本**（採用）：作業系統層級的觸發，服務開不開都會跑；碰得到
本機資料庫；用家用 IP，與手動爬取的網路條件完全相同（因此不會出現「手動可以、排程被擋」
這種只在正式跑才現形的失敗）。

## Consequences

- **兩個行程共用一個 SQLite 檔案。** 常駐的 web 服務（長連線讀取）與排程叫起來的 CLI
  （寫入）會同時碰同一個檔案。預設的 rollback journal 下，寫入會擋住讀取，web 服務必然
  撞上 `database is locked`。**因此 WAL 與 `busy_timeout` 是這個部署形態的必要條件，
  不是最佳化**——理由寫在 `db.py` 的 `connect()` 旁邊。

- **服務組裝必須抽成共用的一份。** 三個入口（web 服務、`scripts/crawl.py`、
  `scripts/backfill_fx_month.py`）用同一組物件，組裝規則只能有一個地方說了算，否則會各自
  漂移：某一個忘了開 WAL、某一個用了不同的請求間隔——而這種漂移只在正式跑的時候才現形。
  這就是 `services.py` 的 `build_services()` 存在的理由。

- **自動化與可觀測性必須同刀交付。** 改成自動之後，失敗會變成安靜的：爬取結果原本只活在
  按下按鈕那一次的瀏覽器回應裡。因此本刀同時長出三層——**爬取帳本**（每輪的流水帳）、
  **頁面過期警示**（被動）、**心跳／死人開關**（主動）。沒有後者就不允許前者。

- **死人開關是唯一抓得到「沉默」的機制。** 爬取跑了但出錯，帳本記得住；爬取**根本沒跑**
  （電腦關機、排程被停用、腳本崩潰），帳本什麼也不會有——出事的行程沒辦法通知你它沒跑
  起來。心跳判斷的對象因此是「該來的沒來」，不是錯誤訊息。

- **`POST /api/market/crawl` 維持同步**，不改成 202 ＋ 輪詢。FastAPI 的同步端點跑在
  threadpool 裡，客戶端斷線不會中止它——爬取照樣跑完、資料照樣入庫，唯一的損失是看不到
  那份報告，而帳本正好補上這一塊。少一組前端狀態管理，行為反而更誠實。

- **最熱門的卡一天一次仍可能漏。** 那 2 張若一天實際成交 30 筆，每天只撈最新 20 筆仍會
  漏掉 10 筆。這不影響市值（近 30 天中位數只需要樣本），但會讓未來的「熱門度」低估。
  改成一天多輪可以緩解，但那是另一刀，且需要先量到真實的漏失率才值得做。

- **排程只在電腦開著時跑。** 這是接受的限制：漏掉的那天補不回來，但死人開關會在該來的
  心跳沒來時通知到手機，所以漏掉這件事本身不會是安靜的。
