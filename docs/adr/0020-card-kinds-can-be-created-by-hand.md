# 卡種列可由使用者手動新增，且確認之前就能掛持有品

卡種列不再只能來自 Notion CSV 的 seed。使用者可以手動新增一個卡種列，它以
`pending`（待確認）狀態進入既有的待確認清單；**在它被確認到 SNKRDUNK 的 apparel
之前，持有品就已經可以掛上去**。

## Context

ADR-0012 定下「持有品掛在卡種列上」，但沒有說卡種列從哪裡來——當時的答案是隱含的：
全部來自 Notion CSV 的 seed，那 68 個卡種就是全世界。

持有品 CRUD 讓這個隱含答案破功。收藏者買到一張**沒有過的**卡時，沒有卡種列可以掛，
於是最常見的情境反而記不下來——CRUD 變成只能記重複的卡。

土法是手改 CSV 再重啟服務（卡種 seed 每次啟動都跑且不覆寫既有狀態，所以確實可行）。
但那要求使用者為了記一筆購入去編輯一個匯出檔，而該檔案的角色早已由 ADR-0013 定為
**一次性的歷史補登入口**，不是日常操作介面。

## Considered Options

**新增卡種時必須同時完成行情對應**（否決）：新增卡種就跳進搜尋 → 挑候選 → 確認的
流程，走完才算數。好處是資料庫裡不會出現「沒有 apparel 的卡種」。

否決的理由是它把兩件不同的事綁在一起。記帳的時機是**剛買完**，行情對應要向 SNKRDUNK
搜尋、要挑候選、要人判斷——若搜尋當下連不上、或候選裡沒有那張卡，購入紀錄就記不成。
**外部來源的可用性不該決定我記不記得住自己買了什麼。**

**另建一張「使用者自訂卡種」表**（否決）：與 seed 來的卡種分開存放。這會讓每一個查詢
都要 union 兩張表，而且「一個卡種」這件事在系統裡會有兩種形狀。ADR-0008 已經定下卡種
的唯一鍵是系列＋卡號＋卡名，兩張表只是把同一個概念切成兩半。

**手動新增，進入既有的待確認清單**（採用）：新的卡種與 seed 來的卡種是**同一種東西**，
走同一條確認流程。唯一鍵（系列＋卡號＋卡名）就是重複的把關者，靠資料庫的唯一約束擋，
不另外查一次。

## Consequences

- **一行新的對應邏輯都不用長。** 新卡種落進待確認清單之後，搜尋、確認、抓卡圖全部沿用
  已經寫好的流程，使用者也不必學一套新的操作。

- **持有品可以掛在還沒有 apparel 的卡種上。** 這種持有品**不顯示市值、不顯示未實現
  損益**——缺市值就讓欄位不存在，不是 null 也不是 0，因為 0 會被讀成「不賺不賠」。
  總市值另外報出「還有幾張沒有市值」，才不會被讀成已經涵蓋全部。

- **系列代碼永不收斂這條規則跟著適用**（ADR-0011）。手動輸入 `SVP` 與 `SV-P` 會得到兩個
  不同的卡種列，這是正確的：它們是不同的系列，不是同一個系列的兩種寫法。輸入的原始
  寫法逐字保存，正規化值另存。

- **打錯字會製造出一個多餘的卡種列。** 使用者輸入 `MEGA Lucaric` 時系統無從得知那是
  筆誤——卡名是唯一鍵的一部分（ADR-0008），系統不能替它猜。那個多餘的列會停在待確認
  清單裡，因為搜尋不到對應的 apparel；這是**看得見的**後果，不是安靜的錯誤。目前沒有
  刪除卡種列的機制，需要時另開票。

- **seed 與手動新增共用同一組正規化規則。** 兩份規則會漂移，而漂移的後果是「同一張卡
  變成兩個卡種列」——持有品分裂到兩邊，市值也跟著分裂，而且兩邊看起來都是對的。
