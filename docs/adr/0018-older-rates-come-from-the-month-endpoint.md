# 更早的匯率取自月份端點，但不接進自動流程

臺銀的 `flcsv/0/{YYYY-MM}/JPY` 提供單一月份的牌告，**格式與 L6M 完全相同**，實測可回溯至 **2023-09**。日常爬取維持使用 L6M；月份端點只做成補登腳本（`scripts/backfill_fx_month.py`），**不接進爬取流程**。

## Context

ADR-0014 的 Consequences 寫著：

> 歷史只回溯約六個月（實測 2026/02/26 ～ 2026/08/25）。若日後需要更早的匯率，這個來源不夠，得另尋。

**這句話是錯的。** 同一個路徑把 `L6M` 換成 `2026-02` 就是那個月的牌告，欄位、數值、編碼全部相同，現有解析器一行不改就吃得下。

會發現是因為 L6M 的形狀比原本以為的更麻煩：它不是「回溯六個月」的固定界線，而是一個**固定 124 個營業日的滾動視窗**，進一天、出一天。實測兩次抓取只差一天：

| 抓取日 | 涵蓋範圍 | 天數 |
|---|---|---|
| 2026-08-25 | 2026-02-26 ～ 2026-08-25 | 124 |
| 2026-08-26 | 2026-03-02 ～ 2026-08-26 | 124 |

滾掉 `2026-02-26`、補進 `2026-08-26`。因此**成交日一旦滾出視窗就再也換算不了**，那筆成交會永久待審。第一次真實爬取就撞上了：兩張冷門的 CP2 老卡有 8 筆二月成交卡在待審。

## Considered Options

**接進自動流程**：爬取時若某個日期落在手上最舊的匯率之前，就自動去抓那個月。技術上不難，但要多一層「哪些月份抓過」的帳本（現行帳本記的是 `requested_through` 單一水位，不適用於補洞），換來的是一個罕見情境——日常爬取每天跑，新成交永遠落在 L6M 內。

**改成只用月份端點**：規則反而更單純（抓需要的月份、抓過的不重抓、當月除外），也不再有滾動視窗的陷阱。但全新資料庫的第一次爬取會變成每個月一個請求，而且要重寫既有的帳本邏輯與測試。

**做成補登腳本**（採用）：自動流程一行不改，需要時人工跑一次。專案擁有者的判斷是這種情況很少見——冷門卡的成交會隨每日爬取自己累積回來，不需要一直往回補。

## Consequences

- `BOT_MONTH_JPY_URL` 只被腳本使用，正式流程碰不到它。腳本走 `MarketService.convert_pending`，不自己實作一份換算——換算規則只能有一個地方說了算。
- **回溯有底**：實測 2023-09 可用、2023-08 與更早回**空白（0 bytes）**。未來月份（如 2026-09）回 57 bytes 的「很抱歉，本次查詢找不到任何一筆資料！」。兩種失敗都被既有偵測擋下（分別是「沒有任何日圓牌告」與「臺銀回『查無資料』」），不會被讀成「那天沒有匯率」。
- 若日後補登變成常態，就該改採「只用月份端點」那個選項——它的規則比滾動視窗乾淨。屆時這份 ADR 是起點。
