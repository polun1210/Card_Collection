# 介面現況與交接

這份文件寫給**接手 UIUX 階段的人**。它回答四件事：現在的介面長什麼樣、哪些東西
**不能動**、動手改的時候**測試會擋你哪裡**、哪些東西**已知該動但刻意還沒動**。

它不是設計規範，也不取代 `CONTEXT.md`。詞彙一律以 `CONTEXT.md` 為準，決策一律以
`docs/adr/` 為準——本文若與那兩者衝突，是本文錯了。

---

## 1. 技術現況（先知道這個，才不會提出做不到的設計）

- **沒有前端框架、沒有建置步驟**。三個頁面都是 Jinja2 樣板，CSS 寫在各頁的
  `<style>` 裡，JS 寫在各頁的 `<script>` 裡。改樣式＝改樣板，存檔重整就看得到。
- **零外部資源**。全站沒有任何 `<link>`、CDN、字型檔或圖示庫。這是刻意的：這是個
  跑在自己電腦上的個人工具，不該因為外部網站掛掉而變醜或變慢。
  - 副作用：`font-family` 指定了 `"Noto Sans TC"` 但**沒有載入它**，所以只有本機
    裝了才會生效，否則落到 `system-ui`。要用指定字型就得決定「要不要為此引入外部
    資源」，那是一個要明講的取捨。
- **JS 只做三件事**：走勢圖繪製與 hover、更新行情的按鈕、持有品增刪改的對話框，
  外加卡片展開時抓動能，以及抽屜卡圖的傾斜與反光（手寫，ADR-0024）。**其餘畫面在沒有 JS 的情況下就是完整的**——分頁切換用的是
  `radio + :checked`，不等腳本。這個性質值得保留。
- 版面寬度：首頁與持有品頁 `max-width: 78rem`，卡種對應頁 `72rem`。

## 2. 三個頁面

| 路由 | 頁面 | 給誰用 | 樣板 |
|---|---|---|---|
| `/` | 收藏總覽 | **日常主畫面**，打開就看到自己的收藏 | `portfolio.html` |
| `/holdings` | 持有品逐筆明細 | 對帳用，一列一個卡種、逐筆展開 | `holdings.html` |
| `/queue` | 卡種對應（待確認清單） | 後台作業，把卡種對到 SNKRDUNK | `queue.html` |

`/` 是根路徑而 `/queue` 不是，這是刻意的：**這是收藏儀表板，不是後台工具**。

### `/` 收藏總覽的區塊（由上而下）

1. **總覽數字**（`.totals`）— 未實現損益、報酬率、已實現損益、持有中張數與成本、
   總市值、已售出張數
2. **行情新鮮度**（`.freshness`）— 上次成功更新是多久以前，超過 24 小時變警示色
3. **工具列**（`.toolbar`）— 更新行情、**新增持有品**、兩個頁面連結
4. **走勢圖**（`.trend`）— 單條總市值面積線（ADR-0025），hover 讀數附總成本，
   區間鈕 `7D / 1M / 3M / YTD / ALL`
5. **卡圖牆**（`.wall`）— 一格一個卡種，分「持有中／已售出」兩個分頁

### 卡圖牆一格的結構

收合時（`<summary>`）顯示卡圖、卡名、系列代碼、報酬率；已售出的另外把成本、淨賺、
售出日也放在收合狀態就看得到（**終局的數字不必展開**）。

展開後（持有中）依序是：成本、市值、未實現損益、**動能**、**流動性**、每一張。
「每一張」逐筆列出購入日與成本，每一筆各自帶 `售出／編輯／刪除`。
已售出展開後是每一筆的售出日與售出價，各自帶 `改回持有中／編輯／刪除`。

## 3. 共用片段：行為共用，外觀不共用

`templates/` 底下 `_` 開頭的是被 `{% include %}` 進去的片段：

| 片段 | 內容 | 被誰用 |
|---|---|---|
| `_market_freshness.html` | 行情新鮮度的 markup | `/`、`/holdings` |
| `_market_script.html` | 更新行情按鈕的行為 | `/`、`/holdings` |
| `_holding_editor.html` | 持有品增刪改的對話框與行為 | `/`、`/holdings` |

**分工是刻意的：這些片段只共用行為與 markup，不共用樣式。** 對應的 CSS 各頁自己寫
一份。理由是版面預期會被重做，共用樣式會讓兩頁被綁在一起改——想單獨調整首頁時，
會發現動一行就把持有品頁也改了。

UIUX 階段若決定要建立共用的設計 token 或樣式表，**這個分工可以推翻**，但請當成一
個明確的決定去做（並補一張 ADR），不要順手改掉。

## 4. 目前的視覺語彙

> ⚠️ 下表是**舊的淺色值**。配色方向已定為單一深色系（ADR-0022），這些值會在版面重做時整份改寫，並在深色底上重新校對對比度。慣例（等寬數字、顏色只用在數字上、走勢線不用漲跌色）不變，只換色值。

| 用途 | 值 | 備註 |
|---|---|---|
| 上漲／獲利 | `#0b7a4b` | 綠 |
| 下跌／虧損／錯誤 | `#b91c1c` | 紅 |
| 警示（過期、匯率抓不到） | `#b45309` | 琥珀 |
| 次要文字 | `#6b7280` | 灰 |
| 框線 | `#d1d5db`（外）／`#e5e7eb`（內） | |
| 圖片底色／佔位 | `#f3f4f6` | 見下方待辦 |
| 連結、焦點 | `#2563eb` | |

其他慣例：

- **數字一律 `font-variant-numeric: tabular-nums`**（等寬數字），縱向對得齊
- **顏色只用在數字上**。走勢圖的線是 teal（`--trend-line`），不帶漲跌語意——
  那條線講的是「總市值多少」，不是「賺賠」
- **不足與空狀態各有各的表現**，幾種刻意長得不一樣，不可以合併成同一種灰字：
  - 這個卡種近期沒成交 → `.expired` 琥珀色「已過期 N 天」
  - 整個系統沒更新成功 → `.freshness.stale` 整塊變琥珀
- **指標還沒到位的空狀態** → `.soon` 虛線圓角標籤（「資料累積中」「敬請期待」）
  ＋ `.why` 一句說明為什麼

## 5. 不可協商的約束

以下每一條都來自 `CONTEXT.md` 或 ADR，**視覺重做時不能違反**。它們看起來像細節，
但每一條都是為了不讓畫面說謊。

1. **缺數字就讓它不存在，不顯示 0，也不顯示 `—` 以外的假值。**
   0 會被讀成「不賺不賠」「不漲不跌」，那是把缺資料講成一個結論。
2. **未實現損益與已實現損益永不混入同一個數字。** 兩者必須分開呈現。
3. **報酬率一律 `(結果 − 成本) ÷ 成本`，不使用倍數。** 全站唯一定義。
4. **市值旁必須並列樣本形狀**（幾筆成交／涵蓋哪段期間）。ADR-0015。
   一個由兩筆成交撐起來的價，與由二十筆撐起來的價，不該長得一模一樣。
5. **走勢圖的資料逐日帶涵蓋率。** ADR-0021 定義、ADR-0025 把它從畫面上拿掉：
   `/api/portfolio` 的 trend 仍回傳每天的 `valued_kind_count`／`held_kind_count`，
   圖上不顯示。曲線前段的爬升有一部分是涵蓋率補齊，不是行情——這是使用者接受的取捨。
6. **行情新鮮度必須與市值出現在同一個畫面上。** 停擺的爬取若不出聲，三週前的數字
   看起來與今天的一模一樣。
7. **空狀態不是暫時的鷹架。** 新買進的卡種永遠會經歷「還沒有動能」的階段，資料補齊
   之後這個狀態依然存在。它要長得像刻意的設計，不是壞掉的畫面。
8. **流動性的兩個半邊必須並列**，不可以只先開熱門度那一半。存世多但成交少，與存世
   多且成交多，是完全不同的兩張卡。
9. **沒有市值的卡種仍然要留在牆上。** 消失會被讀成「我少了一張卡」，那比一格沒有
   數字嚴重得多。
10. **手機是主要的唯讀場景，首頁永不橫向捲動。** 卡圖牆用 `auto-fill` 自己換行，
    刻意不用表格。（`/holdings` 與 `/queue` 是對帳與後台，允許表格橫捲。）
11. **刪除持有品前必須明確確認，且說得出是具體哪一筆**（卡種、購入日、成本），
    已售出的還要說出會讓已實現損益少多少。不是一句抽象的「確定嗎」。

## 6. 重做版面時，測試會擋你哪裡

約三十條測試斷言在 HTML 字串上。**其中只有一部分是真的紅線，其餘紅了應該改測試而
不是改設計。** 先分清楚這三層，才不會被綁住手腳。

判準是專案自己的規範：**重寫實作但行為不變時，測試不該紅。** 第二、三層違反了這一
條——它們的意圖是對的，只是借用了實作細節來表達那個意圖。

### 第一層：紅線，不能違反

這些斷言守的是 §5 的約束。它們紅了代表畫面開始說謊，**要改的是設計不是測試**。

```python
assert "倍" not in html                          # 報酬率不用倍數
assert f"{value['sample_count']} 筆" in html      # 市值必並列樣本（ADR-0015）
assert f"{sample_from}～{sample_to}" in html      # 同上，涵蓋期間
assert "已過期 41 天" in html                     # 近 30 天無成交要說出過期天數
assert "敬請期待" in page                         # 流動性的空狀態有明確文字
assert "資料累積中" in page                       # 動能的空狀態有明確文字
assert "PSA 10 張數" in page                      # 流動性的理由要說出兩個半邊
assert "Mew" in html                              # 沒有市值的卡種仍在牆上
assert 'name="viewport"' in page                  # 手機讀得到
```

金額與百分比的格式斷言（`{:,}`、`{:+.1%}`）也屬於這一層：它們守的是「數字要顯示、
而且用全站同一種寫法」。

### 第二層：意圖對，寫法綁死了實作

```python
assert "auto-fill" in html                    # 意圖：格子自動換行、頁面不橫捲
assert "overflow-x" not in html               # 意圖：頁面本身永不橫向捲動
assert "<table" not in page                   # 意圖：卡圖牆不用表格排版
assert ".wall .soon" in page                  # 意圖：空狀態有自己的樣式
assert 'id="wall-tab-held" checked' in html   # 意圖：持有中是預設分頁
assert 'class="tblwrap"' in page              # 意圖：持有品頁的表格可橫捲
assert f"{momentum['return_rate']:+.1%}" not in page   # 意圖：動能不隨頁面一起算
```

每一條的**意圖**都該保留，**寫法**都該讓路：

- 改用 `flex-wrap` 或 container query 取代 `auto-fill` → `auto-fill` 那條誤紅
- 在卡片展開區用 `<table>` 列出逐張明細（語意上其實合理）→ `<table>` 那條誤紅
- 給某個內部元素加上合法的橫向捲動 → `overflow-x` 那條誤紅
- 改用 JS 切分頁而非 `radio + :checked` → `checked` 那條誤紅
- 重新命名 CSS 類別 → `.wall .soon` 那條誤紅

遇到這些，**改測試讓它表達意圖而不是實作**。例如「頁面不橫捲」比較好的測法是實際
量測渲染寬度，而不是搜尋 CSS 屬性字串——但那需要瀏覽器，目前的測試堆疊沒有。在引入
之前，退而求其次的作法是：改寫斷言使其對應新的實作，並在測試裡把**意圖**寫進註解。

### 第三層：綁死 JS 函式名與 data 屬性

約十六條，集中在 `test_portfolio_actions.py` 與 `test_holdings_crud.py`：

```python
assert 'onclick="openSale(this)"' in page      # 還有 openCreate / openEdit / openUnsell / openDelete
assert 'data-purchase="2026-03-15"' in page    # 還有 data-cost / data-kind / data-realized / data-id
assert 'id="editor"' in page
assert "location.reload()" in page
assert "detailOf" in page
```

意圖是「操作入口就在那一筆旁邊」「確認訊息說得出是具體哪一筆」「操作完成畫面自動
反映」「失敗說得出原因」——這四件事是 §5 第 11 條的紅線，**但用什麼函式名、什麼屬性
名、用不用 `location.reload()` 完全不是**。

前端一旦重寫，這一層會整批紅。**這是預期中的，不是你弄壞了東西。**

### 交接時的實務建議

1. 動工前先跑一次 `uv run python -m pytest -q`，把當下的紅燈記下來當基準線
2. 每改一塊就跑一次，只看**新增**的紅燈
3. 新增的紅燈先問「這條屬於哪一層」，再決定改設計還是改測試
4. 若第一層紅了，停下來——那代表畫面正在說謊，不是版面問題

## 7. 已知該動、刻意還沒動

### 7.1 卡圖框比例錯了，每格浪費一半空間 ⭐ 優先

`aspect-ratio: 10/7` 出現在五處（`portfolio.html` ×1、`holdings.html` ×2、
`queue.html` ×2），搭配 `object-fit: contain` 與 `background: #f3f4f6`。

**它是個過期的值。** git 記錄很明確：

| commit | 事件 |
|---|---|
| `d3c1e76` | 待確認清單接上 SNKRDUNK，寫下 `aspect-ratio: 10/7` |
| `d82ce77` | **之後**才加入裁切（`images.py` 的 `crop_border`） |

`10/7` = 1.43，對應的是 SNKRDUNK **未裁切**的原圖畫布 1000×730（≈1.37）。裁切上線
後卡圖變成直的（約 0.72），這個值沒有回頭改，還被複製到另外兩頁。

實測全部 69 張卡圖，各候選值的留白比例：

| 值 | 比例 | 平均留白 | 最差 |
|---|---|---|---|
| `10/7`（現況） | 1.4286 | **49.6%** | 51.0% |
| `7/10` | 0.7000 | 2.6% | 36.1% |
| `5/7` | 0.7143 | **1.6%** | 34.8% |
| `63/88`（實體卡真實尺寸 63mm × 88mm） | 0.7159 | **1.6%** | 34.6% |

卡圖實際比例：最窄 0.700、中位 0.718、最寬 1.095。

**為什麼留給這個階段而不是順手改掉**：換值不是終點。改成直式後卡圖牆每格高度會從
約 10.7rem 變成約 17.6rem（**整面牆高約 1.6 倍，捲動距離 +65%**），會立刻逼出另外
三個決定，它們應該一起做：

- 格子寬 `minmax(9.5rem, 1fr)` 還合適嗎
- 要不要改用 `object-fit: cover`（裁掉邊緣填滿，留白歸零但會切到卡緣）
- 那塊 `#f3f4f6` 底色還要不要留

`5/7` 與 `63/88` 數據上並列最佳，差別在**哪個值自帶理由**——`63/88` 是實體卡的真實
尺寸，寫進 CSS 時註解自己就寫好了。

沒有任何測試鎖住這個值，改動不會有紅燈保護，也不會有紅燈阻擋。

### 7.2 一張卡圖裁切結果異常

`data/images/744296.webp`（MEGA Lucario 錯體版）是 **668×610，比例 1.095**，
其餘 68 張都在 0.70~0.72。就算換上最佳比例，它那一格仍會有約 35% 留白——
上表的「最差」欄就是它。推測是去背有雜點，讓 `Image.getbbox()` 裁不乾淨。

這是資料問題不是版面問題，但會在版面上現形，所以記在這裡。

### 7.3 配色改單一深色系 — 方向已定（ADR-0022），尚未實作

三頁的配色以深色系為**唯一**基準：不做淺色版、不隨作業系統切換，任何時候打開都是
設計時決定的那套深色（ADR-0022）。

目前仍是舊狀態：§4 的顏色表是寫死的淺色值，`color-scheme` 仍宣告為 `light dark`，
所以作業系統切深色時 `#f3f4f6`（圖片佔位底色）會變成一塊刺眼亮白——這是「宣告了
支援、實際上沒支援」的最糟中間狀態。

實作內容留給版面重做時一起做：

- §4 每個顏色值在深色底上重新校對對比度，紅綠尤其要防刺眼與色弱不友善
- 圖片佔位底色 `#f3f4f6` 換成深色中性底，與 §7.1 的卡圖框待辦一起決定
- `color-scheme: light dark` 改為 `color-scheme: dark`（保留宣告，讓瀏覽器原生元件
  跟著深色；不是刪除）
- 是否把顏色抽成共用 CSS 變數、要不要因此推翻 §3，由這個階段決定並補 ADR

### 7.4 三頁的樣式各寫一份

`portfolio.html` 與 `holdings.html` 幾乎逐字相同。若這個階段要建立設計 token，
這幾塊是最明顯的起點。

### 7.5 卡牌立體特效（傾斜＋反光）— 已實作（選 A，手寫），見 ADR-0024

起點是這個 repo：<https://github.com/simeydotme/pokemon-cards-css>（GPL-3.0，8.2k star，
CSS-Tricks 上那篇 holographic trading card effect 的出處）。作者在 README 置頂自薦了一個
輕量版：<https://github.com/simeydotme/hover-tilt>（MIT）。

以下是 2026-09-13 讀過兩邊原始碼之後的盤點（歷史紀錄）。**後來實作時改為手寫，見 ADR-0024。**

#### 能用的是「傾斜＋反光」，不是「彩虹 holo」

那個特效是分層疊出來的，而**兩層的可用性天差地遠**：

```
.card                     ← 3D 透視容器（perspective: 600px）
 └ .card__translater      ← 位移＋縮放
    └ .card__rotator      ← rotateX / rotateY ── 滑鼠帶動的傾斜
       ├ img              ← 卡面圖
       ├ .card__shine     ← 彩虹 holo 層 ✗ 本專案用不了
       └ .card__glare     ← 反光層       ✓ 可以用
                             ↑ 兩層都靠 CSS 變數驅動：
                               --pointer-x/y、--pointer-from-center、
                               --rotate-x/y、--background-x/y、
                               --card-scale、--card-opacity
```

`glare`（反光）是一個跟著游標跑的放射狀白光 ＋ `mix-blend-mode: overlay`，**不挑卡**。
`shine`（彩虹 holo）是重複線性漸層 × 材質圖 × blend-mode × `clip-path`，**很挑卡**。

**四個理由讓 `shine` 在本專案用不了：**

1. **沒有稀有度資料，而且是刻意沒有。** 那 20 幾支 rarity CSS 是靠 `data-rarity="rare holo"`、
   `data-subtypes` 這些屬性派送的。但 `CONTEXT.md` 明文「不區分鑑定公司、不區分分數」，
   **稀有度還列在 `_Avoid_` 清單**（rarity 在寶可夢卡指卡面印刷的稀有度符號，與本系統的
   流動性概念無關）。`card` 表只有 `series_raw` / `number_raw` / `card_code` / `name_en` /
   `name_ja`，沒有 rarity 欄位。派不出去。
2. **`clip-path` 寫死官方卡框幾何。** `--clip: inset(9.85% 8% 52.85% 8%)` 指的是「標準卡框的
   圖框視窗」。我們的圖是 SNKRDUNK 商品照裁切過的，裁切幅度不一致（§7.2 的
   `744296.webp` 比例 1.095 就是異常值）。對不準就是一塊歪掉的色帶。
3. **卡圖是實拍，holo 已經烙在照片裡。** `91147.webp`（リザードン V SR）照片上的彩虹紋路
   是拍出來的。再疊一層合成彩虹＝雙重 holo。
4. **效能。** 62 格 × 5 層，每層帶
   `will-change: transform, opacity, background-image, background-size, background-position,
   background-blend-mode, filter`。§5 第 10 條說手機是主要的唯讀場景。

**一個值得記下的巧合**：那份 CSS 的 `--card-aspect: 0.718`，與 §7.1 實測 69 張卡圖的中位比例
`0.718`、以及最後採用的 `63/88`（0.716）幾乎完全一致。它本來就是照實體卡比例寫的。

> 實作時的補充（ADR-0024）：使用者看過樣品後選了「整卡彩虹光帶，但淡一點」。它與 shine 不同，
> 所有卡套同一種光帶，不需要稀有度資料；理由 3 的雙重 holo 疑慮使用者看過後接受，透明度降到 .3 減輕之。

#### 兩個候選做法

| | **A. 只用在卡片明細抽屜** | **B. 卡圖牆 62 格也上** |
|---|---|---|
| 範圍 | 一次一張大卡（`_portfolio_wall.html` 的 `.drawer__art`） | 每一格 `.wall .art` |
| 效能風險 | 無。同時只有一張在動 | 高。要節流（只對 hover 中那格啟用）、要實測手機 |
| 動機是否對得上 | 對。抽屜本來就是「仔細看這張卡」的場景 | 牆的任務是「用認圖的方式找卡」，特效反而干擾掃視 |
| 工作量 | 小 | 中，且有效能風險要先實測 |
| 對 §5 約束的影響 | 無 | 無（特效不改任何數字），但捲動流暢度是體感風險 |

還有第三條路留著：**不引入任何檔案，自己移植 `base.css` 的 glare 那段 ＋ 約 40 行 vanilla JS。**
好處是零依賴、沒有授權問題；代價是彈簧物理（spring）的手感要自己調，不會像原版那麼順。

#### 決定：暫定 A

理由是**先用最小的代價看到效果**。A 做完之後如果覺得值得，再決定要不要往牆上推；
**B 不該在沒看過 A 的實際效果之前就做**——它的成本幾乎全在效能調校上，而那筆成本只有在
「已經確定這個特效值得」之後才划算。

什麼情況下才該重新考慮 B：A 上線後實際用了一陣子，**而且**在手機上實測 62 格同時掛載
特效的捲動幀數可以接受。

#### 用 hover-tilt 而不是 pokemon-cards-css

> 已改為手寫，見 ADR-0024（動工前發現 npm 標 MPL-2.0、GitHub 標 MIT，授權不一致，且 bundle 內含 Svelte runtime）。

| | pokemon-cards-css | **hover-tilt** |
|---|---|---|
| 授權 | GPL-3.0（傳染性 copyleft） | **MIT** |
| 形式 | Svelte 專案 ＋ 27 張材質圖 ≈ 4.4 MB | **Web Component**，`dist/hover-tilt.js` 單檔 180,717 bytes |
| 建置步驟 | 要 Vite | **不用**，`<script type="module">` 就跑 |
| 前端框架 | Svelte | **原始碼裡沒有**（Svelte runtime 已編進那支檔案） |
| 稀有度資料 | 必要 | 不需要 |

介面（v1.0.0）：`<hover-tilt tilt-factor="1.5" scale-factor="1.05" glare-intensity="0.8">`，
屬性用 kebab-case，對外露出 `--hover-tilt-opacity` / `--hover-tilt-rotation-x/y` 等 CSS 變數，
內部可用 `::part(container)` / `::part(tilt)` 調整。

#### 實作前必須先處理的四件事

1. **這會動到 §1 的兩條明文性質**，所以**要補一張 ADR**，不要順手做掉：
   - 「零外部資源」——把 `hover-tilt.js` 抓下來放進 `src/card_collection/static/` 就守得住
     （跟 `design.css` 一樣是本機檔案，npm 或任何 CDN 掛掉都不影響）。要在 ADR 裡明講
     這條規矩的意思是「**執行期不依賴外部網站**」而不是「不准用別人的程式碼」。
   - 「沒有前端框架」——那支檔案裡面**包著一份 Svelte runtime**。原始碼裡看不到框架，
     但它確實在 bundle 裡。這是取捨，要寫明白，不要假裝沒這回事。
2. **`prefers-reduced-motion`** 要處理。
3. **`.art` 目前是 `object-fit: contain` ＋ 深色底**（§7.1 的決定）。卡圖四周有留白時，
   傾斜與反光會作用在「圖片元素」而不是「卡的形狀」上，看起來會怪。要先確認反光層是
   貼著卡面還是貼著容器。
4. **測試**：這個改動不碰任何數字，§6 第一層的紅線一條都不會動到。頂多動到第二層
   （CSS 類別名）。

#### 不要走的路

- 不要為了讓 `shine` 能用而去補一個 rarity 欄位。那會把 `CONTEXT.md` 明文排除的概念
  請回系統裡，代價遠大於視覺收穫。
- 不要用 CDN 載 `hover-tilt`。§1 那條規矩的存在理由就是這個。

## 8. 資料從哪裡來

畫面上的每個數字都是伺服器算好的，前端**不重算任何金額**。

| 端點 | 餵給誰 |
|---|---|
| `GET /api/portfolio` | 首頁的全部：總覽數字、走勢圖、新鮮度、卡圖牆 |
| `GET /api/cards/{apparel_id}/holdings` | 卡片**展開時**才取：動能、流動性、該卡種的持有品與市值 |
| `GET /api/cards/{apparel_id}/image` | 卡圖 |
| `POST /api/market/crawl` | 「更新行情」按鈕 |
| `POST/PATCH/DELETE /api/holdings...` | 增刪改對話框 |

兩個值得知道的設計：

- **走勢圖的資料一次全給**。`ALL` 是其他四個區間的超集合，切區間是在瀏覽器裡切片，
  零延遲、不打 API。
- **動能是展開那一刻才取的**，卡圖牆的列表回應不背負它。牆上有六十幾格，為了使用者
  實際會展開的那一兩格，把其餘全部都算一次並不划算。
