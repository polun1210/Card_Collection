01

這是什麼

一個只給自己看的網頁儀表板，回答一個問題：我這批寶可夢鑑定卡現在值多少台幣，比我當初花的多還是少。

它取代目前用來記帳的 Notion 資料庫，成為收藏資料的唯一存放處。市場行情全部來自 SNKRDUNK（日本），每天自動更新一次。

在範圍內

  • 寶可夢卡，PSA 10
  • SNKRDUNK 日本市場成交
  • 持有中與已售出的損益
  • 整體市值走勢圖
  • 新增／編輯／售出／刪除持有品

明確不做

  • eBay 與任何第三方付費行情 API
  • 比較頁與多卡並列比較
  • 個別成交紀錄的畫面呈現
  • 其他鑑定公司與其他分數的區分
  • UI 美化、LLM 問答（延後）
02

領域模型

整場對談最重要的一個發現：規格裡的「卡」其實同時指三種不同的東西。把它們分開之後，後面所有問題才有辦法回答。

卡種（Card）
一款可被唯一識別的卡，權威定義來自 SNKRDUNK 的 apparel。市值、動能、流動性都掛在卡種上。 避免：卡片、商品、product
持有品（Holding）
你實際擁有或曾經擁有的某一張實體卡。同一卡種可有多筆，各有自己的購入日與成本。實際資料中 Charizard S8b 187 有 7 筆，成本從 2,885 到 3,300 不等——這正是不能用「平均成本」建模的證據。 避免：收藏、庫存、inventory
成交紀錄（Sale）
市場上某一次已完成的買賣，與你是否持有無關。不對使用者顯示，它是市值與熱門度的原料。 避免：交易、transaction
市值（Market Value）
一個卡種在某一天的價值 ＝ 該卡種近 30 天成交的中位數。全站只有這一個定義。近 30 天無成交時沿用最後一次算得出的值，並標註已過期幾天。
流動性（Liquidity）
由兩個數字共同構成：PSA 10 張數與近 3 個月成交筆數。兩者分開看沒有意義——存世 1,204 張但三個月只成交 18 筆，跟存世 1,204 張且成交 200 筆，是完全不同的兩張卡。
待審（Quarantined）
爬到但無法高信心確認為「單張、PSA 10、屬於此卡種」的成交。不參與任何計算，等待人工判定。

換匯只走一條路徑：JPY 原幣（不可變）→ 成交當日匯率 → TWD。匯率一經寫入即固定，永不以今日匯率回頭重算歷史——否則整條走勢圖會隨匯率上下平移，昨天看到的圖今天就不一樣。

05

已驗證的事實

以下每一條都是實際跑過、不是查來的說法。

✓SNKRDUNK 有可用的 JSON API：GET /v1/apparels/{id} 回傳 英文卡名、日文卡名、官方去背卡圖、結構化卡種代碼。不需要瀏覽器自動化。
✓商品頁為伺服器端渲染，圖片網址在原始 HTML 裡；CDN 無防盜連，四種尺寸皆可直接下載。robots.txt 只禁止 /en/v1/*。
✓PSA 族群報告不需要 cert number，按系列與卡號查即可。PSA 官網受 Cloudflare 保護，但 PriceCharting 提供同樣資料且 PSA 與 CGC 分欄、純 SSR。
✓eBay 官方確實無法取得成交價：Finding／Shopping API 已於 2025-02-05 停用，Browse API 只有在售，Marketplace Insights 不開放新申請。
✓TCGdex 對日版卡覆蓋不足：102 筆持有品中僅 30 筆有卡圖、20 筆完全查無。這是改用 SNKRDUNK 當卡種主檔的直接原因。
✓成交紀錄端點已解出：GET /v3/products/{productCatalogId}/trading-history，參數 range／condition_code／variant_id，免登入。路徑上的 id 是 productCatalogId，不是 apparel id——用錯會回 200 空資料而不報錯。舊記錄的 /v1/apparels/{id}/used/listings 並不存在（見 ADR-0007）。
✓成交明細 trades 固定最多 20 筆且無分頁；走勢圖 chart 可回填至 2023 年，但為每日聚合、價格不等於任何一筆實際成交，只能當參考線，不可寫入成交紀錄。
✓三類髒資料已縮減為一類：variant_id（枚数）可在來源端排除多張一組，trades 本身即已完成成交、不含下架未成交。只剩離群值需自行處理。
!Notion 的 102 筆需對應到 SNKRDUNK 的 apparel id，兩套編碼不相通。採半自動比對＋人工確認，絕不全自動——對錯一張卡不會報錯，只會安靜地錯下去。
06

決策總表

依提問輪次排列。輪次不是流水號——它記錄了依賴順序：每一輪的問題，都必須等前一輪答案確定後才問得出來。

34 項決策
編號決定理由
第一輪 · 根：這是什麼
Q1卡種／持有品／成交三者分開同卡種多張、成本各異；平均成本模型會丟失這個資訊
Q2市值 ＝ 30 天中位數，砍掉 1D成交稀疏，單筆離群值會讓總市值劇烈跳動
第二輪 · 領域界線
Q6卡種主檔採外部權威自建等於維護一份沒有盡頭的卡片百科
Q7不設語言欄位系列代碼本身已決定語言，多一欄就多一個能自相矛盾的地方
Q8走勢圖只算持有中；已售出資料照存未實現與已實現是兩個問題，混在同一數字會看不懂
第三輪 A · 資料源重新定錨
A1免費匯率 API，含歷史匯率回填舊成交需要當日匯率，台銀牌告的歷史要自己存
A2保留 PSA 10 張數，改用 PriceCharting不需 cert number，且能繞過 PSA 官網的 Cloudflare
A3SNKRDUNK 為卡種主檔唯一權威主檔與價格同源，不會出現抓不到價格的鬼卡
A4Notion 對應採半自動＋人工確認全自動對錯不會報錯，只會安靜地錯
A5UI 不標註「僅日本市場」單人使用，使用者自己清楚；若有第二人須重新檢視
第三輪 B · 計算規則
B1百分比一律為報酬率，非倍數同畫面兩種算法遲早看錯一次
B2走勢圖採「當時持有」今日持有回推會回頭改寫歷史，圖會說謊
B3能回填多少就回填多少，不補值補值是製造假資料，會讓所有線失去可信度
B4白名單清洗，其餘進待審稀疏樣本的中位數，混進一筆垃圾是毀滅性的
B5Python ＋ SQLite ＋ FastAPI ＋ 輕量前端此規模下 PostgreSQL 只帶來維運負擔
第三輪 C · 營運
C1零成交時沿用舊值＋標註過期天數卡沒有變得不值錢，只是沒人在賣
C2工具完全取代 Notion單一真實來源，不做雙寫
C4移除比較頁使用者判定自己沒有這個需求
C5每天全部跑一遍，不分批68 個卡種的規模不需要分批；分批會讓市值最舊差七天
C6被動健康摘要，不發通知安靜說謊的儀表板比沒有儀表板更糟；通知會被習慣性忽略
第四輪 D · 畫面結構
D1保留 PSA 10 張數指標成本降至每月爬 68 頁，且它回答動能答不出的問題
D2收藏總覽一格一個卡種市值等四個數字都屬於卡種；逐張列會重複印 90% 的資訊
D3移除交易明細畫面（資料照存）畫面移除，但市值與熱門度的原料仍需保留
D4完整 CRUD：新增／編輯／售出／刪除沒有刪除功能，第一次手滑輸錯就會開始不信任整個系統
D5新增時直接搜尋 SNKRDUNK只搜本地主檔會形成死結，新卡永遠加不進來
D6卡圖牆＋點擊展開細節九個數字同時推到面前，等於一個都沒推到
第五輪 E ／ F · 收尾
E1張數與熱門度合併為「流動性」兩者分開看幾乎沒意義，並列才有意義
E2走勢圖疊上成本線兩線之間的距離即未實現損益，讓圖自己說話
E3持有中依市值高到低排序穩定的排序能形成肌肉記憶；按漲跌幅會每天洗牌
E4已售出獨立卡圖牆，不需展開已售出的數字是終局的，沒有再看一層的需求
E5全部視為 PSA 10，不區分鑑定使用者已於 Notion 統一並保有完整備份
F1已售出同樣採卡種聚合兩區同一套邏輯，眼睛不用切換模式
07

下一步

以下順序刻意如此：對應表沒建好之前，任何價格都是不可信的，所以它排在爬蟲之前。

  1. 解出成交紀錄端點的參數 —— 已完成由前端 JS bundle 解出 /v3/products/{productCatalogId}/trading-history。成交明細只回最新 20 筆，走勢圖可回填至 2023 年。詳見 ADR-0007。
  2. 建立 68 個卡種的對應表以系列＋卡號向 SNKRDUNK 撈候選，附卡圖分批送出，由你用看的確認。這是整個系統的地基。
  3. 匯入 Notion 的 102 筆持有品含 11 筆已售出。卡號補零至三位、SVP 正規化為 SV-P，原始值一律保留不改寫。
  4. 建立爬取與清洗管線每日全量 68 個卡種，白名單過濾，不確定的進待審佇列。
  5. 接上匯率與 PSA 張數匯率每日，張數每月。
  6. 做畫面Figure 區與 Collection 兩個分頁，外加完整 CRUD。
